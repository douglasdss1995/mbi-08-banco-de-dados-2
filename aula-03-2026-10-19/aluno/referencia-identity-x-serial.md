# IDENTITY ou serial? Como numerar a chave primária

Leitura de apoio da aula 3 (DDL: *Data Definition Language*, a linguagem que define a estrutura das tabelas). Nos exemplos
do curso, toda chave primária que o banco numera sozinho é escrita assim:

```sql
CREATE TABLE cliente (
    cod_cliente integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome        varchar(100) NOT NULL
);
```

Em tutoriais, em código antigo e nas respostas da IA (Inteligência Artificial) você vai ver outra forma, com `serial`. As
duas funcionam. Este texto explica a diferença e por que o curso usa a primeira.

## O que cada um é

| | `serial` | `GENERATED ALWAYS AS IDENTITY` |
|---|---|---|
| Origem | Atalho antigo do PostgreSQL | Padrão SQL (*Structured Query Language*), no PostgreSQL desde a versão 10 |
| É um tipo? | Não. É `integer` com um `DEFAULT` | Não. É uma propriedade da coluna |
| Numeração | Uma sequência comum, criada por baixo, com nome próprio | Uma sequência interna da coluna |
| Aceita valor digitado à mão? | **Sim**, sem avisar | **Não**, o banco recusa |
| Funciona em outros bancos? | Só no PostgreSQL | Tem equivalente no Oracle, DB2 e SQL Server |

Para ver que o `serial` é só um atalho, crie uma tabela com ele e rode `\d` no `psql`:

```sql
CREATE TABLE s (id serial PRIMARY KEY, nome text);
\d s
```

A coluna aparece como `integer`, com o padrão `nextval('s_id_seq'::regclass)`. O PostgreSQL criou uma sequência
`s_id_seq` por baixo e escreveu o `DEFAULT` por você. (O que é uma sequência está em
[`referencia-sequences.md`](referencia-sequences.md).)

## Os três motivos para preferir o IDENTITY

### 1. O banco recusa o código digitado à mão

Com `GENERATED ALWAYS`, quem tenta informar o código recebe um erro:

```sql
CREATE TABLE a (id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, nome text);
INSERT INTO a (nome) VALUES ('x'), ('y');          -- ids 1 e 2
INSERT INTO a (id, nome) VALUES (10, 'manual');
```

```text
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETALHE:  Column "id" is an identity column defined as GENERATED ALWAYS.
DICA:  Use OVERRIDING SYSTEM VALUE to override.
```

No `serial`, o mesmo comando seria aceito. E isso cria um problema que aparece **depois**:

```sql
INSERT INTO s (nome) VALUES ('x');                 -- id 1, pela sequência
INSERT INTO s (id, nome) VALUES (2, 'manual');     -- aceito: a sequência não fica sabendo
INSERT INTO s (nome) VALUES ('y');                 -- a sequência entrega o 2
```

```text
ERROR:  duplicate key value violates unique constraint "s_pkey"
DETALHE:  Key (id)=(2) already exists.
```

O erro só estoura quando a sequência alcança o número digitado, às vezes semanas depois da causa. Com `IDENTITY`, o
erro vem no mesmo instante, na linha que errou. É a ideia da aula 8: o banco se defende sozinho.

### 2. A sequência faz parte da coluna

No `IDENTITY`, a sequência é interna à coluna: você não a cria, não a escolhe e não a usa por engano em outra tabela. No
`serial`, a sequência é um objeto comum, com nome próprio (`s_id_seq`), que qualquer comando pode usar (por exemplo,
`nextval('s_id_seq')` em outra tabela). O PostgreSQL a apaga junto com a tabela, mas ela continua sendo um objeto separado.

Há também uma diferença de permissão: com `serial`, quem recebe `INSERT` na tabela também precisa de permissão na
sequência (sem ela, o erro é `permission denied for sequence s2_id_seq`). Com `IDENTITY`, só o `INSERT` basta.

### 3. É o padrão

A sintaxe `GENERATED ... AS IDENTITY` é a do padrão SQL. Quem aprende assim consegue ler e escrever o mesmo em outros
bancos, e o PostgreSQL recomenda esta forma para código novo.

## As três variações

```sql
id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY       -- só o banco numera (a do curso)
id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY   -- o banco numera, mas aceita um valor digitado
id serial PRIMARY KEY                                      -- o atalho antigo
```

`BY DEFAULT` é útil para **carregar dados que já têm código** (por exemplo, uma migração). Depois da carga, ajuste a
sequência para não repetir os valores (veja `setval` na referência de sequências).

### E se eu precisar mesmo informar o código?

Com `ALWAYS`, existe uma saída **explícita**, que deixa claro no comando que você sabe o que está fazendo:

```sql
INSERT INTO a (id, nome) OVERRIDING SYSTEM VALUE VALUES (10, 'forçado');
```

Atenção: o valor forçado **não avança a sequência**. Se a numeração chegar ao 10 depois, vai dar chave duplicada, como no
`serial`. Por isso, depois de forçar, ajuste a sequência com `setval`.

## Por que `integer`?

O `IDENTITY` precisa de um tipo inteiro. Usamos `integer`, que guarda até cerca de 2,1 bilhões. Se a tabela puder passar
disso (por exemplo, registros de log de um sistema grande), use `bigint`:

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

## Pegadinhas que valem nas duas formas

- **A numeração tem buracos.** Um `INSERT` desfeito por `ROLLBACK` consome o número e não o devolve. Se você inserir 3
  linhas, desfizer uma e inserir outra, os códigos serão 1, 2, 3 e 5. Isso é normal: o código identifica a linha, não
  conta quantas existem.
- **Apagar linhas não reutiliza o número.** Se você apaga o cliente 7, o próximo cliente novo **não** é o 7.
- **O código não tem significado.** Não use `cod_cliente` para ordenar por "quem chegou primeiro" com certeza, nem
  para contar linhas. Use uma coluna de data e `count(*)`.
- **Se a chave já existe no negócio** (como a placa do veículo), não precisa de `IDENTITY`: use a própria placa.
  A escolha entre chave natural e chave substituta está na aula 9.

## Resumo

- Escreva `integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. É o jeito atual, padronizado, e que recusa código digitado à
  mão.
- Reconheça o `serial` quando aparecer: ele funciona, mas é o atalho antigo.
- Se a IA sugerir `serial`, pode trocar. Anote no README que você conferiu.
